# Security Evaluation Report: Group 7

- **Target**: Group 7 (DreamTeam7)
- **Evaluator**: Person 3 (Dina), Identity and Access Control (AuthN, DAC, MAC, RBAC)
- **Environment**: Windows 11, Python 3.12.11, asyncssh 2.24.1. Server run from
  `targets/DreamTeam7/server/server.py` on `127.0.0.1:2222`. Tested with an asyncssh
  SFTP client using a pinned host key.

## 1. Overview & Setup

Three setup steps were needed before testing, none of which are weaknesses:
- The submission ships no host key (correctly ignored by Git), so one was generated with
  `ssh-keygen`, as their README instructs.
- The flag is not planted by default, so `ctf/setup_flag.py` was run to write it to
  `/projects/confidential/flag.txt`.
- The group does not document passwords and theirs resist guessing (see "What resisted"), so a
  known demo password was set for each user with `tests/p3/g7_provision.py` to allow login, and
  the original `users.json` was restored afterwards with `--restore`. This is a testing aid, not
  a finding.

Users: `alice` (analyst, internal), `bob` (admin, internal), `carol` (analyst, confidential),
`eve` (guest, public). The server loads all data files cleanly at startup.

Functional check, normal users:

| Check | Result |
|:---|:---|
| alice / bob / carol / eve correct password login | PASS (all four) |
| alice wrong password login | PASS (rejected) |
| eve list `/public` (allowed) | PASS |
| eve list `/` (not allowed, root is internal) | PASS (denied) |
| alice write `/projects/plan.txt` (allowed) | PASS |

| carol read the flag (allowed) | PASS |
| eve / alice / bob read the flag (not allowed) | PASS (all denied) |

The access control gate behaves exactly as their README describes, and the audit log records the
correct reason for each decision.

## 2. Vulnerabilities Identified

No authentication or authorization break was found. The two items below are low severity and the
group already lists both in its own "Known limitations".

### Finding 1: Login lockout can be used to block a user [LOW]

**(1) Affected submission:** Group 7.

**(2) Description** (denial of service, design tradeoff). `auth.py` locks an account for 60 seconds
after 5 failed logins, keyed on the username only. The lockout is a required feature, so this is
not a mistake, and the group documents it. Because usernames are public, anyone can send 5 wrong
passwords for a user and that user's correct password is then refused during the lockout.

**(3) Reproduction** (`tests/p3/p3_probe.py g7`, lockout step): send 5 wrong passwords for `bob`,
then log in as `bob` with the correct password. It is refused while locked.

**(4) Preconditions:** network access and a known username. No login needed.

**(5) Impact:** a user can be blocked from logging in on demand. Clears after 60 seconds but is
easy to repeat. Availability only. Severity low.

**(6) Evidence:** `evidence/p3_probe.log` (lockout step, correct password rejected).

**(7) Suggested fix:** rate-limit per source IP instead of per username.

### Finding 2: Locked account answers faster than a wrong password [LOW]

**(1) Affected submission:** Group 7.

**(2) Description** (timing side channel). In `check_password`, a locked account returns before any
scrypt hashing, while a wrong password runs the full hash first. The response-time difference tells
an attacker whether an account is currently locked. The group documents this too.

**(3) Reproduction:** time a login to a locked account versus a wrong-password login to an unlocked
account; the locked one returns noticeably sooner.

**(4) Preconditions:** network access and a known username.

**(5) Impact:** minor information leak (lock state). Severity low.

**(6) Evidence:** code read of `server/auth.py` (the lock check returns before `_scrypt`).

**(7) Suggested fix:** run the dummy hash before returning on a locked account so the timing matches
a normal failed login.

### What resisted

Pretty much everything. Attempts that failed:

- **Password guessing.** About 45 common and name-based passwords were tried offline against the
  stored scrypt hashes; none matched (`evidence/p3_pwcrack.log`). Passwords are salted scrypt with
  constant-time compare.
- **User enumeration.** `auth.py` runs a full dummy hash for unknown users, so an unknown name does
  not return faster than a known one (the one timing gap is the locked-account case, Finding 2).
- **Authorization bypass.** `policy.py` has no decision cache (so Group 2's cache bypass does not
  apply here), normalizes paths, denies by default on unknown user, operation, missing label or
  missing owner entry, and requires DAC AND MAC AND RBAC with per-user deny checked first. The flag
  is denied to eve, alice and bob each for the correct reason and allowed only to carol. The audit
  log proves it:
  ```json
  {"user":"eve","op":"read","path":"/projects/confidential/flag.txt","allowed":false,"reason":"denied: DAC: other lacks 0o4 ...; MAC: no read up (public -> confidential); RBAC: denied (read) for roles ['guest'] ..."}
  {"user":"alice","op":"read","path":"/projects/confidential/flag.txt","allowed":false,"reason":"denied: MAC: no read up (internal -> confidential)"}
  {"user":"carol","op":"read","path":"/projects/confidential/flag.txt","allowed":true,"reason":"allowed: DAC: owner ...; MAC: confidential may read confidential; RBAC: allowed (read) via analyst:/projects"}
  ```
- Path traversal, symlink and handle attacks are handled before policy by `canonicalize()` and
  `safe_join()`, and the group ships its own `ctf/attack.py` covering 18 such attempts. Those are in
  Person 2 and Person 4's area, not identity and access control.

## 3. Reproduction & Exploit Steps

```powershell
# one-time setup
ssh-keygen -t ed25519 -N '""' -f targets\DreamTeam7\server\ssh_host_ed25519_key
python -I targets\DreamTeam7\ctf\setup_flag.py
python -I tests\p3\g7_provision.py targets\DreamTeam7\server\data\users.json

# boot (Terminal 1)
$env:PYTHONPATH = "$PWD\targets\DreamTeam7\server"
python -s -P targets\DreamTeam7\server\server.py

python tests\p3\p3_probe.py g7

# restore their original users.json afterwards
python -I tests\p3\g7_provision.py targets\DreamTeam7\server\data\users.json --restore
```

## 5. Overall Evaluation

Strengths. Both authentication and authorization are well built. Salted scrypt with constant-time
compare and a dummy hash against enumeration, strong passwords, and a clean DAC, MAC and RBAC gate
with no cache, default-deny, per-user deny-first, and a full audited reason for every decision. The
flag is protected by all three models at once, and I could not get it as eve, alice or bob.

Weaknesses. Only two low-severity items, both disclosed by the group: the username-keyed lockout can
block a user (Finding 1) and a locked account answers faster than a wrong password (Finding 2).

What resisted. Password guessing, user enumeration, and every authorization path to the flag.

Overall resistance: high. No identity or access-control break was found; the only issues are minor
and already documented by the group.
