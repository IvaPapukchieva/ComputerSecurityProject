## 1. Overview & Setup

- **Target System**: Hardened SFTP v3 server implementation by Group 7 over `asyncssh` with custom authentication (`auth.py`), strict triple-gate access control policy (`policy.py`), and atomic path canonicalization (`server.py`).
- **Environment Tested**: Python 3.14 on Windows 11 with `asyncssh` and `pytest`.
- **Predefined Users Tested**:
  - `alice` (Role: `analyst`, Clearance: `internal`, Group: `analyst`)
  - `bob` (Role: `admin`, Clearance: `internal`, Group: `admin`)
  - `carol` (Role: `analyst`, Clearance: `confidential`, Group: `analyst`, Owner of `/projects/confidential`)
  - `eve` (Role: `guest`, Clearance: `public`, Group: `guest`)
- **Flag Location**: `/projects/confidential/flag.txt` (Mode: `0660`, Owner: `carol:analyst`, Clearance: `confidential`).
- **Flag Content**: `FLAG{group07_sftp_wins}`
- **Hint Location**: `/public/ctf_hint.txt` (`"The flag is kept strictly confidential. Only authorized eyes may view it."`).
- **Access Control Baseline**:
  - Group 7 implemented a strict conjunctive policy gate requiring $\text{DAC} \land \text{MAC} \land \text{RBAC}$.
  - Bell-LaPadula MAC strictly enforces "no read up" ($\text{clearance}(u) \ge \text{classification}(o)$) and "no write down" ($\text{clearance}(u) \le \text{classification}(o)$).
  - Path canonicalization in `server.py` rejects null bytes, Windows drive letters, UNC paths, ADS streams, backslashes, and directory traversal tokens (`..`).
  - Read exfiltration attempts by `eve`, `bob`, and `alice` are stopped by DAC and MAC gates.

## 2. Vulnerabilities Identified

### Vulnerability 7.1: Blind Flag Destruction / Integrity Violation via Policy Misconfiguration (Bell-LaPadula Write-Up + Over-Permissive DAC Group)

* **(1) Affected submission(s)**: Group 7 (`DreamTeam7`)
* **(2) Vulnerability description**:
  Group 7 designed their access control gate to prevent unauthorized *read* access to `/projects/confidential/flag.txt` by enforcing Bell-LaPadula "no read up". However, Bell-LaPadula's $\star$-property explicitly allows **write-up** ($\text{clearance} \le \text{classification}$, $1 \le 2$).
  In `data/dac_owners.csv`, Group 7 configured group ownership of `/projects/confidential` as `analyst` with `dir_mode=770` and `file_mode=660` (granting both Read and Write to members of group `analyst`).
  Because user `alice` has role `analyst` (giving group membership in `analyst` and RBAC write permissions on `/projects`), all three models evaluate to `True` for write operations:
  $$\text{DAC (group 0660: write allowed)} \land \text{MAC (internal} \le \text{confidential: write-up allowed)} \land \text{RBAC (analyst on /projects: write allowed)} = \mathbf{True}$$
  While `alice` cannot read the flag, an attacker authenticated as `alice` can open `/projects/confidential/flag.txt` with `SSH_FXF_WRITE | SSH_FXF_TRUNC` and arbitrarily overwrite, truncate, or corrupt the confidential flag file.
* **(3) Reproduction steps**:
  1. Authenticate to the SFTP server as `alice` (`clearance: internal`, `role: analyst`).
  2. Send an `SSH_FXP_OPEN` request for `/projects/confidential/flag.txt` with flags `SSH_FXF_WRITE | SSH_FXF_TRUNC` (mode `0x12`):
     ```python
     async with conn.start_sftp_client() as sftp:
         async with sftp.open("/projects/confidential/flag.txt", "wb") as f:
             await f.write(b"CORRUPTED_BY_ALICE")
     ```
  3. The server checks `policy.authorize("alice", "write", "/projects/confidential/flag.txt")`:
     - DAC allows (group `analyst` has `0o2` write bit).
     - MAC allows (clearance `internal` may write to `confidential`).
     - RBAC allows (`analyst` has `write` grant on prefix `/projects`).
  4. The server returns an open file handle.
  5. The attacker writes arbitrary data. The original flag is permanently overwritten.
  6. When legitimate confidential user `carol` opens the file, the flag is gone and replaced by the attacker's payload.
* **(4) Exploitability**: High. Requires only credentials of standard internal analyst account `alice`.
* **(5) Impact / implications**: High (Integrity). While confidentiality of the original flag is maintained against reading, the integrity of confidential files is destroyed. Lower-clearance users can blind-overwrite or truncate sensitive confidential files.
* **(6) Evidence**:
  - Automated test in `tests/p5/test_dreamteam7_security.py`: `test_vuln_unauthorized_flag_overwrite_via_bell_lapadula_writeup` passes.
  - Server audit log:
    ```json
    {"timestamp": "2026-11-24T09:42:25+00:00", "user": "alice", "op": "write", "path": "/projects/confidential/flag.txt", "allowed": true, "reason": "allowed: DAC: group has 0o2 on /projects/confidential (file mode 0o660); MAC: internal may write confidential; RBAC: allowed (write) via analyst:/projects"}
    ```
* **(7) Suggested fix**:
  Restrict DAC permissions on `/projects/confidential` in `data/dac_owners.csv` to `file_mode=0600` and `dir_mode=0700` so only owner `carol` has write access, or enforce strict integrity controls (e.g. Biba Model: no write-up) in conjunction with Bell-LaPadula.

### Vulnerability 7.2: Unauthenticated Targeted Account Lockout Denial of Service (DoS)

* **(1) Affected submission(s)**: Group 7 (`DreamTeam7`)
* **(2) Vulnerability description**:
  In `server/auth.py`, failed login attempts are tracked in a global in-memory dictionary `_failed[username]`. If 5 consecutive failed passwords are submitted for a given username, `_locked_until[username]` is set to `time.monotonic() + 60` seconds.
  Because login requests require no pre-authentication, captcha, or IP rate-limiting, an unauthenticated remote attacker can intentionally flood 5 invalid passwords for any target user (such as `carol` or `bob`). This immediately locks the targeted account, preventing legitimate authorized users from logging in. An attacker running a simple 60-second loop can indefinitely deny access to administrative and confidential identities.
* **(3) Reproduction steps**:
  1. An unauthenticated attacker connects to the SFTP server port.
  2. Send 5 authentication requests for user `carol` with incorrect passwords:
     ```python
     for _ in range(5):
         auth.check_password(users, "carol", "wrong_guess")
     ```
  3. `auth.py` records 5 failures and sets `_locked_until["carol"] = time.monotonic() + 60`.
  4. Carol attempts to log in with her legitimate credentials:
     ```python
     auth.check_password(users, "carol", carol_valid_password)
     ```
  5. The server immediately rejects the login with `"account locked"` without verifying the password.
* **(4) Exploitability**: High. Requires no credentials; executable remotely by any network client.
* **(5) Impact / implications**: High (Availability). Total denial of service against specific high-privilege users (`carol`, `bob`), freezing all legitimate confidential workflows.
* **(6) Evidence**:
  - Automated test in `tests/p5/test_dreamteam7_security.py`: `test_vuln_account_lockout_denial_of_service` passes.
  - Audit trail excerpt:
    ```json
    {"timestamp": "2026-11-24T09:42:25+00:00", "user": "carol", "op": "login", "path": null, "allowed": false, "reason": "wrong password, account locked for 60s"}
    {"timestamp": "2026-11-24T09:42:25+00:00", "user": "carol", "op": "login", "path": null, "allowed": false, "reason": "account locked"}
    ```
* **(7) Suggested fix**:
  Track lockout thresholds per client IP/network address rather than solely per username, or introduce exponential delays/proof-of-work before triggering global account freezes.
