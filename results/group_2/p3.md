# Security Evaluation Report: Group 2

- **Target**: Group 2 (DreamTeam2)
- **Evaluator**: Person 3 (Dina), Identity and Access Control (AuthN, DAC, MAC, RBAC)
- **Environment**: Windows 11, Python 3.12.11, asyncssh 2.24.1. Server run from
  `targets/DreamTeam2/server/server.py` on `127.0.0.1:2222`. Tested with an asyncssh
  SFTP client using a pinned host key (`tests/p3/g2_known_hosts`).

## 1. Overview & Setup

The server starts cleanly and loads all data files. Three users were tested: `alice`
(professor, confidential), `bob` (student and TA, internal), `eve` (student, public).
Passwords are in the group's README.

Functional check, normal users:

| Check | Result |
|:---|:---|
| alice correct password login | PASS |
| alice wrong password login | PASS (rejected) |
| eve correct password login | PASS |
| eve write `/projects/x.txt` (not allowed) | PASS (denied) |
| eve list `/admin` (not allowed) | PASS (denied) |
| eve read the flag (not allowed) | PASS (denied) |
| alice list `/projects` (allowed) | PASS |

DAC, MAC and RBAC each work correctly on a normal request. The right users are allowed
and the wrong users are denied. The problem is a cache that skips these checks (Finding 1).

Evidence: `evidence/p3_functional.log`.

## 2. Vulnerabilities Identified

### Finding 1: Authorization bypass through the allow-cache [HIGH]

**(1) Affected submission:** Group 2.

**(2) Description** (authorization bypass). `PolicyEngine.authorize()` in `server/policy.py`
checks an allow-cache before it runs the DAC, MAC and RBAC checks, and returns early on a hit.
The cache key keeps only the first part of the path:

```python
def _cache_key(self, user, op, full_path):
    top = full_path.strip("/").split("/", 1)[0]   # only the first segment
    return (user, op, top)
```

So `/projects/pwn.txt` and `/projects/confidential/flag.txt` get the same key
`(bob, read, "projects")`. One allowed read anywhere under `/projects` caches an allow that
is then reused for every file under `/projects`, including the confidential flag.

**(3) Reproduction** (`tests/p3/g2_exploit.py`, as `bob`):
1. `put /projects/pwn.txt` (allowed, a TA may write here).
2. `get /projects/pwn.txt` (allowed, this fills the cache for read under `/projects`).
3. `get /projects/confidential/flag.txt` returns the flag from the cache, with no
   DAC, MAC or RBAC check.

Control: before step 2, a direct read of the flag by `bob` is denied.

**(4) Preconditions:** attacker is logged in as any user who can do one allowed action in
the target folder. `bob` does this by uploading a file he is allowed to upload.

**(5) Impact:** bypasses all three access models at once. `bob` has internal clearance and
reads a confidential file (read-up), which MAC and DAC both deny on the direct path. This is
how an unauthorized user reads the protected flag. Supports Person 5's flag capture. Severity high.

**(6) Evidence:** `evidence/p3_cache_bypass.log` and `evidence/p3_audit.jsonl`. The server's
own audit log shows the deny, then the cached allow:
```json
{"user":"bob","op":"read","path":"/projects/confidential/flag.txt","allowed":false,"reason":"DAC deny: Denied for other lacking 'r' bit"}
{"user":"bob","op":"read","path":"/projects/confidential/flag.txt","allowed":true,"reason":"Allowed (cached decision)"}
```

**(7) Suggested fix:** key the cache on the full path, or remove the cache. 

### Finding 2: Login lockout can be used to block a user [LOW]

**(1) Affected submission:** Group 2.

**(2) Description** (denial of service, design tradeoff). `LoginThrottle` in `server/auth.py`
locks an account for 30 seconds after 5 failed logins, keyed on the username only. The lockout
itself is a required feature, so this is not a mistake. The weak point is the keying: because
usernames are public, anyone can send 5 wrong passwords for a user and that user's correct
password is then refused during the lockout. It also counts failures for unknown usernames.

**(3) Reproduction** (`tests/p3/p3_probe.py g2`, lockout step): send 5 wrong passwords for `bob`, then
log in as `bob` with the correct password. It is refused while locked. Repeating every 30
seconds keeps the user out (We are aware that for this project we were required to document the users
so this might not be a weakness depending on what was expected from phase 1 documentation)

**(4) Preconditions:** network access and a known username. No login needed.

**(5) Impact:** a user can be blocked from logging in on demand. Is eliminated after 30 seconds
though but is easy to repeat. Availability only. Severity low.

**(6) Evidence:** `evidence/p3_lockout_dos.log`.

**(7) Suggested fix:** rate-limit per source IP instead of per username, and do not count
failures for unknown usernames.

### Finding 3: README does not match behavior for eve on /projects [LOW]

**(1) Affected submission:** Group 2.

**(2) Description** (documentation). The README says eve has read-only access to `/projects`.
In practice eve cannot read it: MAC denies it (eve is public, `/projects` is internal, read-up)
and DAC denies it (eve is "other", mode `---`). The stated access is not possible.

**(3) Reproduction:** as `eve`, read `/projects`, result is denied (`evidence/p3_functional.log`).

**(4) Preconditions:** none. This is a correctness issue, not an exploit. The system is stricter
than documented, so it fails safe.

**(5) Impact:** misleading documentation. Severity low.

**(6) Evidence:** `evidence/p3_functional.log`.

**(7) Suggested fix:** fix the README, or adjust eve's clearance, role or mode to match it.


## 3. Reproduction & Exploit Steps

Start the server (Terminal 1):
```powershell
Remove-Item targets\DreamTeam2\server\audit.jsonl -ErrorAction SilentlyContinue
$env:PYTHONPATH = "$PWD\targets\DreamTeam2\server"
python -s -P targets\DreamTeam2\server\server.py
```

Run the probes (Terminal 2). Run the exploit first on a fresh server so the cache is
empty. The probe ends with the lockout step, which locks bob for 30 seconds, so run it after.
```powershell
python tests\p3\g2_exploit.py     # Finding 1, cache bypass, flag read by bob
python tests\p3\p3_probe.py g2    # functional + auth checks, then the lockout step
```
Both scripts read `tests\p3\groups.json` for the group's config and build the pinned
host-key file themselves, so there is no separate known-hosts step.

## 5. Overall Evaluation

Strengths. Authentication is solid: per-user salt with scrypt, constant-time compare, a dummy
hash for unknown users to hide timing, and a clean failure on bad data files. No passwords show
up in the logs. The three access models are correct on normal requests and every decision is
audited. The audit log even recorded the attack.

Weaknesses. The allow-cache is the main problem. Its key is too coarse and it skips all three
checks for deeper paths, which is how the flag is read (Finding 1, high). The lockout keying lets
an outsider block a user (Finding 2, low). The README has one access claim that does not match
the code (Finding 3, low).

What resisted. Password hashing and storage, secret leakage in logs, timing-based user
enumeration, and the DAC, MAC and RBAC checks themselves on any request that does not hit the
cache. The access models are sound. Only the cache breaks them.

Overall resistance: medium. Strong authentication and correct core policy, with one high-severity
cache bypass.
