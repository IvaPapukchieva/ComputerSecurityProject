# Security Evaluation Report: Group 10

- **Target**: Group 10 (DreamTeam10)
- **Evaluator**: Person 3 (Dina), Identity and Access Control (AuthN, DAC, MAC, RBAC)
- **Environment**: Windows 11, Python 3.12.11, asyncssh 2.24.1. Server run from
  `targets/DreamTeam10/server/server.py` on `127.0.0.1:2222`. Tested with an asyncssh
  SFTP client using a pinned host key.

## 1. Overview & Setup

Two setup steps were needed, neither a weakness:
- The submission ships only the private host key, so its public key was derived with
  `ssh-keygen -y` to pin the connection.
- The shipped `users.json` holds hashes of discarded random passwords (stated in their README),
  so a known demo password was set for each user with `tests/p3/p3_setpw.py` to allow login, and
  the original file was restored afterwards with `--restore`. This is a testing aid, not a finding.

Users: `bob` (analyst, internal), `carol` (analyst + admin, internal), `alice` (analyst + admin,
confidential), `eve` (guest, public). The server loads all six policy/auth files cleanly.

Functional check, normal users:

| Check | Result |
|:---|:---|
| alice / bob / carol / eve correct password login | PASS (all four) |
| alice wrong password login | PASS (rejected) |
| eve read `/public/welcome.txt` (allowed) | PASS |
| eve list `/projects` (not allowed) | PASS (denied) |
| eve read `/projects/flag.txt` (not allowed) | PASS (denied) |
| bob read `/projects/flag.txt` (allowed) | PASS |
| bob write `/public/x.txt` (not allowed, MAC no write down) | PASS (denied) |
| carol read `/projects/flag.txt` (allowed) | PASS |

The gate behaves as their README describes, and the audit log records the reason for each
decision (for example `bob write /public/x.txt -> MAC`).

## 2. Vulnerabilities Identified

No authentication or authorization break was found. The items below are low severity; the lockout
tradeoff is one the group discloses itself.

### Finding 1: Login throttle can be used to block a user [LOW]

**(1) Affected submission:** Group 10.

**(2) Description** (denial of service, design tradeoff). `auth.py` throttles logins per username
(5 per 60 seconds) and per peer (20 per 60 seconds), counting both failed and successful attempts.
The throttle is a required feature and the group documents the tradeoff. Because usernames are
public, anyone can spend a user's 5 attempts and that user's correct password is refused for the
rest of the window.

**(3) Reproduction** (`tests/p3/p3_probe.py g10`, lockout step): send 5 wrong passwords for `bob`,
then log in as `bob` with the correct password. It is refused while throttled.

**(4) Preconditions:** network access and a known username. No login needed.

**(5) Impact:** a user can be blocked from logging in for up to 60 seconds, repeatable. Availability
only. Severity low. (The per-peer limit does add protection the other groups lack.)

**(6) Evidence:** `evidence/p3_probe.log` (lockout step, correct password rejected).

**(7) Suggested fix:** keep the per-peer limit but do not let per-username attempts from other
sources lock out the real user, for example by separating a wrong-password counter from a
successful-login reset.

### Observation: the flag is placed at an internal path, not a confidential one [INFO]

The flag is at `/projects/flag.txt`, which is labelled **internal**. So bob, carol and alice (all
analysts with internal or higher clearance and staff DAC access) can all read it legitimately. It
is only barred from eve. Placing the flag under `/projects/confidential` (confidential label, 700,
alice-owned) would have limited it to one user, as the other groups did. This is a design weakness
in how much the flag is protected, not an authorization bug: eve is still correctly denied.

### What resisted

- **Authorization bypass.** `policy.py` canonicalizes the path, denies by default on unknown user,
  operation, missing label or missing owner entry, checks the execute bit on every ancestor, and
  requires DAC AND MAC AND RBAC with no cache and no admin bypass. eve is denied the flag by DAC and
  MAC, and bob is denied writing down to `/public` by MAC. The matrix matched the stated rules on
  every probe.
- **Password guessing.** Not applicable in the usual sense: the shipped hashes are random discarded
  passwords, so there is nothing weak to guess (unlike Group 5).
- **User enumeration.** `auth.py` runs a real dummy scrypt for unknown usernames, so timing does not
  reveal which accounts exist.

## 3. Reproduction & Exploit Steps

```powershell
# derive the public host key for pinning (ships only the private key)
ssh-keygen -y -f targets\DreamTeam10\server\ssh_host_ed25519_key > targets\DreamTeam10\server\ssh_host_ed25519_key.pub

# set demo passwords (the shipped hashes are random)
python -I tests\p3\p3_setpw.py targets\DreamTeam10\data\users.json

# boot (Terminal 1); the server adds its own import path
python -s -P targets\DreamTeam10\server\server.py

# probe (Terminal 2)
python tests\p3\p3_probe.py g10

# restore their original users.json afterwards
python -I tests\p3\p3_setpw.py targets\DreamTeam10\data\users.json --restore
```

## 5. Overall Evaluation

Strengths. Strong authentication: salted scrypt with
constant-time compare, a dummy hash against enumeration, and throttling per username AND per peer
with attempts charged before the hash. Authorization is also solid: canonicalization, ancestor
execute checks, default-deny, DAC AND MAC AND RBAC with no admin bypass, and a full audit trail.

Weaknesses. Only the disclosed throttle-based login block (Finding 1, low), and a design choice to
place the flag at an internal path where every staff analyst can read it (Observation).

What resisted. Authorization on every probe, user enumeration, and password guessing.

Overall resistance: high. No identity or access-control break; the flag's exposure to analysts is a
placement choice (explored in CTF part, not here).
