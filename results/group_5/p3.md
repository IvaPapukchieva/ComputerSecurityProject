# Security Evaluation Report: Group 5

- **Target**: Group 5 (DreamTeam5)
- **Evaluator**: Person 3 (Dina), Identity and Access Control (AuthN, DAC, MAC, RBAC)
- **Environment**: Windows 11, Python 3.12.11, asyncssh 2.24.1. Server run from
  `targets/DreamTeam5/server/server.py` on `127.0.0.1:2222`. Tested with an asyncssh
  SFTP client using a pinned host key (built by the probe from the group's public key).

## 1. Overview & Setup

The server starts cleanly, creates its `projects`, `admin` and `public` directories, and
loads all data files. Users: `alice` (admin, confidential), `bob` (analyst, internal),
`eve` (intern, public). The group does not document passwords, but two of them equal the
username (see Finding 1), which is how I got login access.

Functional check, normal users:

| Check | Result |
|:---|:---|
| alice correct password login | PASS |
| bob correct password login | PASS |
| alice wrong password login | PASS (rejected) |
| bob list `/projects` (allowed) | PASS |
| bob write `/projects/p3_probe.txt` (allowed) | PASS |
| bob list `/admin` (not allowed) | PASS (denied) |
| bob read `/admin/flag.txt` (not allowed) | PASS (denied) |
| alice list `/admin` (allowed) | PASS |
| alice read `/admin/flag.txt` (allowed) | PASS |

The access control gate works as described. The right users are allowed and the wrong users
are denied, with a correct reason recorded in the audit log for each decision. The real
weakness here is authentication, not authorization.

Evidence: `evidence/p3_probe.log`.

## 2. Vulnerabilities Identified

### Finding 1: Passwords equal the usernames [HIGH]

**(1) Affected submission:** Group 5.

**(2) Description** (weak credentials). The stored password for `alice` is `alice` and for
`bob` is `bob`. The usernames are public (they are in the README and the data files). So an
attacker guesses the admin password in one try, logs in as `alice` (confidential clearance,
admin role, owner of `/admin`), and reads anything, including the flag. No authorization
weakness is needed. Couldn't guess`eve`'s password.

**(3) Reproduction:**
- Offline check against the stored hashes (`tests/p3/pw_try.py`): `alice -> 'alice'`,
  `bob -> 'bob'`.
- Live (`tests/p3/g5_exploit.py`): log in as `alice` with password `alice`, read
  `/admin/flag.txt`, get the flag. Logging in as `bob` and reading the same path is denied,
  which shows the flag is only reachable because the admin password is guessable.

**(4) Preconditions:** network access and a known username. No prior access needed.

**(5) Impact:** full account takeover of the administrator, which gives read and write over
the whole jail and reads the protected flag. Supports Person 5's flag capture. Severity high.

**(6) Evidence:** `evidence/p3_weakcreds_flag.log` (flag text
`hey there im the flag! you found me`), and `evidence/p3_audit.jsonl`:
```json
{"user":"alice","op":"read","path":"/admin/flag.txt","allowed":true,"reason":"allowed"}
{"user":"bob","op":"read","path":"/admin/flag.txt","allowed":false,"reason":"dac_denied"}
```

**(7) Suggested fix:** set strong, unique passwords and add a minimum-strength policy so a
password cannot equal the username or a common word.

### Finding 2: Username enumeration by response timing [LOW]

**(1) Affected submission:** Group 5.

**(2) Description** (information leak). `verify_password` in `server/auth.py` returns at once
for an unknown username without running scrypt, while a known username runs the full scrypt
hash. The timing difference lets an attacker tell valid usernames from invalid ones. A hardened
version runs a dummy hash for unknown users to keep the time constant.

**(3) Reproduction:** send a login for a known user and for an unknown user and compare response
time. The unknown user returns noticeably faster.

**(4) Preconditions:** network access. No login needed.

**(5) Impact:** confirms which usernames exist. Low here because the usernames are already
public, but it would matter if they were not. Severity low.

**(6) Evidence:** code read of `server/auth.py` (`verify_password` returns `False` before any
hashing when `users.get(username)` is `None`).

**(7) Suggested fix:** run a dummy scrypt for unknown users so the response time does not depend
on whether the account exists.

### Finding 3: Login lockout can be used to block a user [LOW]

**(1) Affected submission:** Group 5.

**(2) Description** (denial of service, design tradeoff). `LoginLimiter` in `server/auth.py`
locks an account for 60 seconds after 5 failed logins, keyed on the username only. The lockout
is a required feature, so this is not a mistake. The weak point is the keying: because usernames
are public, anyone can send 5 wrong passwords for a user and that user's correct password is then
refused during the lockout.

**(3) Reproduction** (`tests/p3/p3_probe.py g5`, lockout step): send 5 wrong passwords for `bob`,
then log in as `bob` with the correct password. It is refused while locked.

**(4) Preconditions:** network access and a known username. No login needed.

**(5) Impact:** a user can be blocked from logging in on demand. Clears after 60 seconds but is
easy to repeat. Availability only. Severity low.

**(6) Evidence:** `evidence/p3_probe.log` (lockout step, correct password rejected).

**(7) Suggested fix:** rate-limit per source IP instead of per username.

### What resisted: the authorization gate

The DAC, MAC and RBAC gate in `server/policy.py` held up. There is no decision cache, so Group 2's
bypass does not apply. Paths are validated, every ancestor needs the execute bit, unknown users,
operations and unlabeled paths are denied, and the final decision is DAC AND MAC AND RBAC. The
flag at `/admin/flag.txt` is denied to `bob` by DAC (mode `0700`, bob is "other"), by MAC (internal
below confidential, no read up), and by RBAC (analyst has no admin grant), so any one of the three
stops him. I did not find an authorization bypass. 

## 3. Reproduction & Exploit Steps

Start the server (Terminal 1):
```powershell
$env:PYTHONPATH = "$PWD\targets\DreamTeam5\server"
python -s -P targets\DreamTeam5\server\server.py
```

Run the probes (Terminal 2). Run the exploit before the probe, since the probe's lockout step
locks bob for 60 seconds.
```powershell
python tests\p3\g5_exploit.py # Finding 1, log in as alice and read the flag
python tests\p3\p3_probe.py g5 # functional + authz checks, then the lockout step
python tests\p3\pw_try.py targets\DreamTeam5\data\users.json # offline proof passwords = usernames
```

## 5. Overall Evaluation

Strengths. The authorization layer is well done: salted scrypt with constant-time compare, a
careful DAC, MAC and RBAC gate with no cache, strict path handling, default-deny, and a full audit
record per decision. I could not bypass the access models.

Weaknesses. The passwords are the problem. Two of three equal the username, so the admin account
is taken over in one guess and the flag falls without touching the access models (Finding 1, high).
Authentication also leaks which usernames exist through timing (Finding 2, low) and the lockout
keying lets an outsider block a user (Finding 3, low).

What resisted. The DAC, MAC and RBAC gate, path handling, and the flag's triple protection against
`bob`. The only route to the flag was the weak admin password.

Overall resistance: medium. Strong access control undermined by trivially guessable passwords.
