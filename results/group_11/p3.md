# Security Evaluation Report: Group 11

- **Target**: Group 11 (DreamTeam11)
- **Evaluator**: Person 3 (Dina), Identity and Access Control (AuthN, DAC, MAC, RBAC)
- **Environment**: Windows 11, Python 3.12.11, asyncssh 2.24.1. Server run from
  `targets/DreamTeam11/server/server.py` on `127.0.0.1:2222`. Tested with an asyncssh
  SFTP client using a pinned host key.

## 1. Overview & Setup

Setup steps, none a weakness:
- `scripts/setup_ctf.py` plants the flag, generates the host key and seeds demo files.
- The host key's public half was exported with asyncssh (the private key's Windows permissions
  blocked `ssh-keygen -y`) to pin the connection.
- bob's real password is known (see Finding 1), but alice's and eve's are not, so a known demo
  password was set for all three with `tests/p3/p3_setpw.py` to run the authz matrix, and the
  original `users.json` was restored afterwards with `--restore`. This is a testing aid.

Users: `alice` (admin, confidential), `bob` (analyst, internal), `eve` (intern, public). The
server loads all policy and auth files cleanly.

Functional check, normal users:

| Check | Result |
|:---|:---|
| alice / bob / eve correct password login | PASS (all three) |
| alice wrong password login | PASS (rejected) |
| eve list `/public` (allowed) | PASS |
| eve list `/projects` (not allowed, no read up) | PASS (denied) |
| eve read the flag (not allowed) | PASS (denied) |
| bob list `/projects` (allowed) | PASS |
| bob read the flag (not allowed) | PASS (denied) |
| bob overwrite the flag (not allowed) | PASS (denied by DAC) |
| alice read the flag (allowed) | PASS |
| alice list `/admin` (allowed) | PASS |

The gate behaves as their README and `policy.md` describe, and each decision is audited with a
per-model `checks` breakdown.

## 2. Vulnerabilities Identified

### Finding 1: Weak, reused password for bob [MEDIUM]

**(1) Affected submission:** Group 11.

**(2) Description** (weak credentials). bob's stored password is `test`. Its salt and hash are
byte-identical to the shared Assignment-1 sample dataset (the same record appears in other groups'
files), so the account passwords are the reused Assignment-1 samples rather than fresh secrets. The
README confirms this ("use the sample password supplied separately in Assignment 1"). `test` is a
4-character dictionary word, guessed offline in one try. Any classmate who has the Assignment-1
samples, or any attacker running a small wordlist, logs in as bob.

**(3) Reproduction** (`tests/p3/pw_try.py`): run the offline guesser against
`targets/DreamTeam11/data/users.json`; bob resolves to `test`. Then log in as bob with that password.

**(4) Preconditions:** network access and a known username. No prior access needed.

**(5) Impact:** account takeover of bob, giving read/write in `/projects` and read of `/public` at
internal clearance. It does **not** reach the confidential flag, which needs alice's clearance, and
alice's password did not fall to the wordlist. Severity medium.

**(6) Evidence:** `evidence/p3_pwcrack.log` (bob -> `test`, salt/hash matching the shared dataset).

**(7) Suggested fix:** set strong unique passwords per account a; add a minimum-length and dictionary check when provisioning.

### Finding 2: Username enumeration by response timing [LOW]

**(1) Affected submission:** Group 11.

**(2) Description** (information leak). `verify_password` in `server/auth.py` returns immediately for
an unknown username without computing scrypt, while a known username runs the full hash. The timing
gap reveals which usernames exist. (Groups 7 and 10 close this with a dummy hash; Group 11 does not.)

**(3) Reproduction:** time a login for a known username versus an unknown one; the unknown one
returns noticeably sooner.

**(4) Preconditions:** network access. No login needed.

**(5) Impact:** confirms valid usernames. Low, since the three names are already public. Severity low.

**(6) Evidence:** code read of `server/auth.py` (`verify_password` returns `False` before hashing
when the record is missing).

**(7) Suggested fix:** compute a dummy scrypt for unknown users so timing does not depend on whether
the account exists.

### Observation: flag overwrite is protected by DAC alone [INFO]

The group discloses this, and the audit log confirms it. bob (internal, analyst) writing the flag
passes MAC (write up is allowed) and RBAC (analyst writes `/projects`), and is stopped only by DAC
(bob is "other" on the `0600` file). Reading the flag is stopped by two layers (DAC and MAC), but
overwriting it rests on one. It holds here, but a single DAC mistake would make the flag writable.
Audit evidence:
```json
{"user":"bob","op":"write","path":"/projects/confidential/flag.txt","allowed":false,"reason":"DAC permissions deny access at /projects/confidential","checks":{"dac":false,"mac":true,"rbac":true}}
```

### What resisted

- **Authorization bypass.** `server/policy.py` canonicalizes and jails the path, denies by default
  on unknown user, operation, missing label or missing DAC entry, checks the execute bit on every
  ancestor, tracks dynamic ownership with atomic state writes, and requires DAC AND MAC AND RBAC with
  no cache and no admin override. The flag is read only by alice and denied to bob and eve, each with
  the correct per-model reason. No bypass found.
- **Targeted-account lockout DoS.** Unlike the other four submissions, Group 11 rate-limits **per
  client IP** (`LoginRateLimiter`), not per username, and a successful login frees its own slot. So
  an attacker flooding wrong passwords exhausts their own IP budget, not a chosen victim's login.
  This avoids the targeted-user DoS the other groups have (the residual cost is that users behind one
  shared IP share the budget).
- **Password guessing** for alice and eve: not cracked by the wordlist (only bob's reused `test` fell).

## 3. Reproduction & Exploit Steps

```powershell
# setup: flag + host key + demo files
python targets\DreamTeam11\scripts\setup_ctf.py
# export the public host key (ssh-keygen -y is blocked by the key's Windows ACL)
python -I -c "import asyncssh; k=asyncssh.read_private_key(r'targets/DreamTeam11/server/ssh_host_ed25519_key'); open(r'targets/DreamTeam11/server/ssh_host_ed25519_key.pub','wb').write(k.export_public_key('openssh'))"

# weak-password evidence (run before changing anything)
python -I tests\p3\pw_try.py targets\DreamTeam11\data\users.json

# set demo passwords to run the authz matrix
python -I tests\p3\p3_setpw.py targets\DreamTeam11\data\users.json

# boot (Terminal 1)
$env:PYTHONPATH = "$PWD\targets\DreamTeam11\server"
python targets\DreamTeam11\server\server.py

# probe (Terminal 2)
python tests\p3\p3_probe.py g11

# restore their original users.json afterwards
python -I tests\p3\p3_setpw.py targets\DreamTeam11\data\users.json --restore
```

## 5. Overall Evaluation

Strengths. A very strong authorization layer: canonicalization, jail resolution, ancestor execute
checks, dynamic ownership with atomic state, default-deny, DAC AND MAC AND RBAC with no admin bypass,
and a detailed per-model audit trail. Authentication uses salted scrypt with constant-time compare,
and the per-IP rate limiter avoids the targeted-user lockout DoS the other groups share.

Weaknesses. The passwords are the weak point: bob is the reused Assignment-1 sample `test`
(Finding 1, medium). Authentication also leaks usernames by timing (Finding 2, low), and flag
overwrite rests on DAC alone (Observation, disclosed).

What resisted. The authorization gate on every probe, alice's and eve's passwords, and the
account-lockout DoS that worked on the other four groups.

Overall resistance: high for authorization, medium for authentication. The only concrete break is
bob's guessable reused password, which does not by itself reach the flag.
