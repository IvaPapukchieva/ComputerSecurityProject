## 2. Vulnerability 11.1: User Enumeration via Authentication Timing Side-Channel

### (1) Affected submission(s)
Group 11 (`DreamTeam11`), specifically `server/auth.py` in function `verify_password`.

### (2) Vulnerability description
In `targets/DreamTeam11/server/auth.py` (lines 140–148):
```python
def verify_password(users: Mapping[str, PasswordRecord], username: str, password: str) -> bool:
    record = users.get(username)
    if record is None:
        return False
    derived_hash = record.derive_hash(password.encode("utf-8"))
    return hmac.compare_digest(derived_hash, record.password_hash)
```
When an unauthenticated client connects and provides a username that **does not exist** in `users`, `verify_password` returns `False` immediately via a sub-microsecond dictionary lookup.

When an unauthenticated client provides a username that **does exist** in `users` (e.g. `alice` or `bob`), `verify_password` executes `record.derive_hash()`. This function invokes `hashlib.scrypt` with heavy key derivation parameters:
```python
hashlib.scrypt(password, salt=self.salt, n=16384, r=8, p=1, maxmem=32 * 1024 * 1024)
```
On typical hardware, `scrypt` computation takes **30 ms – 130 ms**, whereas the non-existent user lookup takes **0.0003 ms – 0.0026 ms**.

This produces an extreme timing discrepancy of over **50,000x** (empirically measured at **336,000x** in local CPU benchmarks, and ~**50,830x** inside the test harness). Even across a high-jitter wide-area network, a 50+ millisecond delay is readily distinguishable, allowing an external attacker to reliably enumerate all valid user accounts on the server without valid credentials.

### (3) Reproduction & Verification steps
1. Run the dedicated test in `tests/p5/test_dreamteam11_security.py::test_vuln_auth_timing_side_channel_user_enumeration`.
2. Observe the latency measurement comparing non-existent username lookup vs. existing username lookup:
   - Non-existent user lookup: `0.0026 ms`
   - Existing user lookup: `132.1611 ms`
   - Timing discrepancy ratio: `50,830.8x`
3. Any candidate username can be tested remotely: queries returning in $< 5\text{ ms}$ indicate invalid usernames; queries returning in $> 50\text{ ms}$ indicate valid accounts.

### (4) Exploitability
**High**. The flaw is remotely accessible via the standard SSH/SFTP authentication handshake without requiring prior authentication. An attacker can use dictionary-based username lists to systematically enumerate users (e.g., discovering `alice`, `bob`, `eve`, `admin`, `operator`).

### (5) Impact / implications
- **CWE-208**: Observable Timing Discrepancy.
- **CWE-200**: Exposure of Sensitive Information to an Unauthorized Actor.
- Enables targeted brute-force and credential stuffing against verified usernames.
- Allows attackers to focus offline password attacks solely on accounts known to hold high clearance (e.g., `alice`).

### (6) Evidence
- Automated test: `tests/p5/test_dreamteam11_security.py::test_vuln_auth_timing_side_channel_user_enumeration` (PASSED).
- Benchmark log output:
  ```text
  [Side-Channel Benchmark] Non-existent: 0.0026 ms, Existing: 132.1611 ms, Ratio: 50830.8x
  ```
- Relevant source code: `targets/DreamTeam11/server/auth.py` lines 140–148.

### (7) Suggested fix / Hardening recommendations
Implement constant-time authentication by deriving a dummy `scrypt` hash with identical parameters when a user record is not found:
```python
# Fixed implementation:
_DUMMY_SALT = os.urandom(16)

def verify_password(users: Mapping[str, PasswordRecord], username: str, password: str) -> bool:
    record = users.get(username)
    if record is None:
        # Perform identical scrypt derivation against dummy salt to equalize timing
        hashlib.scrypt(password.encode("utf-8"), salt=_DUMMY_SALT, n=16384, r=8, p=1, maxmem=32 * 1024 * 1024)
        return False
    derived_hash = record.derive_hash(password.encode("utf-8"))
    return hmac.compare_digest(derived_hash, record.password_hash)
```

## 3. Finding 11.2: Unbounded Buffer Growth in Protocol Framing

### (1) Affected submission(s)
Group 11 (`DreamTeam11`), specifically `server/server.py` in method `data_received`.

### (2) Finding description
In `server/server.py` (lines 261–277):
```python
def data_received(self, data: bytes) -> None:
    self.buf += data
    while True:
        if len(self.buf) < 4:
            return
        pkt_len = int.from_bytes(self.buf[:4], "big")
        if pkt_len > MAX_PACKET:
            self._abort_protocol()
            return
        if len(self.buf) < 4 + pkt_len:
            return
        pkt = self.buf[4:4 + pkt_len]
        self.buf = self.buf[4 + pkt_len:]
        ...
```
While `pkt_len > MAX_PACKET` (256 KB) correctly aborts on oversized frames, if a malicious client sends fragmented data or a 4-byte header specifying a valid `pkt_len` (e.g. 250 KB) and streams small chunks indefinitely across multiple sessions without closing them, `self.buf` accumulates unconsumed data in memory. If thousands of concurrent connections stream partial data slowly, it may lead to resource exhaustion (slowloris-style DoS).

### (3) Suggested fix
Enforce an upper bound on `len(self.buf)` directly upon receiving incoming bytes:
```python
if len(self.buf) + len(data) > MAX_PACKET + 4096:
    self._abort_protocol()
    return
```

## 4. Security Architecture & Attack Resistance Audit

### 4.1 Flag Location & Protection
- **Target Flag**: Seeded via `scripts/setup_ctf.py` into `/projects/confidential/flag.txt` with pattern `FLAG{group11_sftp_<16_hex_chars>}`.
- **Redundant Two-Layer Defense**:
  1. **Discretionary Access Control (DAC)**:
     - `/projects/confidential` is owned by `alice:admins` with directory permissions `0700` (`rwx------`) and file permissions `0600` (`rw-------`).
     - Both `bob` (group `analysts`) and `eve` (group `interns`) fall into the `other` category (`000`). They are denied traverse (`x`), read (`r`), and write (`w`) permissions at the parent directory level.
  2. **Mandatory Access Control (MAC)**:
     - Bell-LaPadula clearance lattice: `public (0) < internal (1) < confidential (2)`.
     - The flag path is labeled `confidential` (level 2).
     - `bob` has clearance `internal` (level 1), and `eve` has clearance `public` (level 0).
     - Under the "no read up" rule ($L(u) \ge L(o)$), both users are strictly forbidden from reading the flag.

### 4.2 Proof of Layer Independence
In `tests/p5/test_dreamteam11_security.py::test_defense_in_depth_layer_independence`, we deliberately weakened one layer at a time:
- **Scenario A (DAC Disabled)**: `/projects/confidential` permissions were opened to `0777` / `0666`. Bob's read attempt was evaluated; MAC intervened and denied access (`MAC no read up (internal < confidential)`).
- **Scenario B (MAC Disabled)**: Bob was elevated to clearance `confidential`. Bob's read attempt was evaluated; DAC intervened and denied access (`DAC permissions deny access at /projects/confidential`).
This verifies that neither layer acts as a single point of failure.

### 4.3 Resistance to Tampering & Blind Overwrite (Comparison with DreamTeam7)
- In **DreamTeam7**, `/projects/confidential` was group-owned by `analysts` with mode `0770` and files mode `0660`. Under Bell-LaPadula "write-up", Bob (internal) could overwrite/truncate Alice's confidential flag (`flag.txt`), destroying its integrity.
- In **DreamTeam11**, `/projects/confidential` has directory mode `0700` owned exclusively by `alice:admins`. Because writing or creating files requires `write + traverse` on the parent directory, DAC rejects Bob's write probe immediately (`checks: {"dac": false, "mac": true, "rbac": true}`). Tampering is prevented.

### 4.4 Resistance to Symlink & Jail Traversal
- In `server/jail.py`, path canonicalization resolves paths against the root, prohibiting path escape characters (`..`), null bytes, and alternative streams.
- On Windows, `jail.py` pins each parent component using Win32 `CreateFileW` with `FILE_READ_ATTRIBUTES` and checks `info.attributes & 0x400` to reject reparse points (symlinks/junctions).
- On POSIX systems, it walks components using `O_NOFOLLOW` with file descriptors (`dir_fd`).
